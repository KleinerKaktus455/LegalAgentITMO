# Тест-кейсы качества работы мультиагентной системы

## Цель
Оценить не только корректность отдельных функций, но и качество поведения агентов: правильность маршрутизации, релевантность выдачи, структуру и достоверность финального ответа, отсутствие галлюцинаций.

## Окружение
- Python 3.11+
- pytest 9.0+
- SQLite in-memory / временный файл
- LLM не требуется для unit-тестов качества; e2e с LLM помечены как `slow`.

---

## AQ-01: Правильность выбора плейбука по запросу
- **Модуль:** `legal_multiagent.agents.orchestrator._rule_playbook`
- **Тип:** unit
- **Шаги:**
  1. Подать запросы: "найди похожие дела", "оцени риск", "напиши апелляцию", "разбери досье", "составь черновик".
  2. Проверить, что выбран `analogs`, `risk`, `appeal`, `dossier`, `draft` соответственно.
- **Ожидаемый результат:** правильная маршрутизация по ключевым словам.
- **Критерий приемки:** ≥ 4 из 5 запросов маршрутизируются правильно.

## AQ-02: План плейбука содержит ожидаемые агенты
- **Модуль:** `legal_multiagent.agents.orchestrator.PLAYBOOKS`
- **Тип:** unit
- **Шаги:**
  1. Для каждого плейбука проверить, что первый узел — `parser`, последний — `respond`.
  2. Проверить обязательные узлы: `retriever` в `analogs`, `risk`, `appeal`, `draft`, `full`; `risk` в `risk`; `appeal` и `draft` в `appeal`.
- **Ожидаемый результат:** структура плана соответствует заявленной функциональности.
- **Критерий приемки:** все плейбуки проходят проверку структуры.

## AQ-03: Parser находит дело по case_id
- **Модуль:** `legal_multiagent.agents.parser.parser_node`
- **Тип:** integration
- **Предусловия:** в хранилище есть дело с известным `case_id`.
- **Шаги:**
  1. Создать состояние с `plan=["parser"]`, `case_id=<id>`.
  2. Вызвать `parser_node`.
- **Ожидаемый результат:** в ответе есть `case`, `case_id`, `case_number`; `steps_done` содержит `"parser"`.
- **Критерий приемки:** карточка извлечена корректно.

## AQ-04: Parser сообщает о ненайденном деле
- **Модуль:** `legal_multiagent.agents.parser.parser_node`
- **Тип:** integration
- **Шаги:**
  1. Вызвать `parser_node` с `case_id="nonexistent"` и `plan=["parser"]`.
- **Ожидаемый результат:** `steps_done == ["parser:skip"]`, в `gaps` есть сообщение о том, что карточка не найдена.
- **Критерий приемки:** система не падает и явно сообщает о пробеле.

## AQ-07: Act Reader извлекает фабулу и резолютивку из сплитов

- **Тип:** unit

## AQ-08: Retriever возвращает релевантные аналоги
- **Модуль:** `legal_multiagent.agents.retriever.retriever_node`
- **Тип:** integration
- **Предусловия:** в хранилище есть дела по статье 105 в регионе Москва и дела по другим статьям.
- **Шаги:**
  1. Подать дело по ст. 105 из Москвы.
  2. Вызвать `retriever_node` с `plan=["retriever"]`.
- **Ожидаемый результат:** топ аналогов имеет ту же статью, регион совпадает чаще, чем для случайной выборки; исключён исходный `case_id`.
- **Критерий приемки:** precision@5 по статье ≥ 80%, precision@5 по региону ≥ 60%.

## AQ-09: Respond формирует финальный ответ без выдуманных данных
- **Модуль:** `legal_multiagent.agents.respond.respond_node`
- **Тип:** unit
- **Предусловия:** подготовлено состояние с `case`, `timeline`, `analogs`, `risk`, `steps_done`.
- **Шаги:**
  1. Вызвать `respond_node`.
  2. Проверить, что `final_answer` содержит реальные `case_id`, `case_number`, статью, исход.
  3. Проверить, что в тексте нет фраз "LLM выдумал" или несуществующих номеров.
- **Ожидаемый результат:** ответ основан только на данных состояния.
- **Критерий приемки:** все переданные факты присутствуют, чужих id нет.

## AQ-11: Полный граф завершается для плейбука dossier
- **Модуль:** `legal_multiagent.graph.run_agent`
- **Тип:** e2e / slow
- **Предусловия:** хранилище содержит дело; LLK может быть выключен.
- **Шаги:**
  1. Запустить `run_agent(query="разбери дело", case_id=<id>, playbook="dossier")`.
  2. Проверить `steps_done`, наличие `final_answer`, отсутствие необработанных `errors`.
- **Ожидаемый результат:** граф проходит узлы `parser → timeline → act_reader → qualification → respond`.
- **Критерий приемки:** шаги совпадают с планом, ошибок нет.

## AQ-12: Оценка риска не даёт оправдательный прогноз без оснований
- **Модуль:** `legal_multiagent.agents.risk.risk_node`
- **Тип:** unit / integration
- **Предусловия:** есть аналоги, большинство — обвинительные приговоры/отказы.
- **Шаги:**
  1. Вызвать `risk_node`.
  2. Проверить `caveats` и `summary`.
- **Ожидаемый результат:** `caveats` содержит предупреждение, что оправдательных мало, и что это не прогноз суда.
- **Критерий приемки:** система не обещает оправдание.
